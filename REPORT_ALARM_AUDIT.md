# REPORT_ALARM_AUDIT

Every app deployment (AuthStack, HmrcStack, AccountStack, BillingStack, ApiStack, OpsStack,
EdgeStack) creates about 136 CloudWatch alarms. The shared environment stacks (ObservabilityStack,
AnalyticsStack, IngestionStack, and friends) add another 27, once per environment. One environment
with a single active deployment — prod, most of the time — carries roughly 163 alarms. CI, which
runs several concurrent feature-branch deployments, multiplies the 136 by however many are live at
once. None of this matches `AWS_COSTS.md`'s working assumption of "~20 alarms" for prod; the real
count is about 7x that.

- Audited: 2026-08-31
- Method: CDK source read only — see "What was skipped" below
- Source: `infra/main/java/co/uk/diyaccounting/submit/` (application stacks in `cdk-application/`,
  environment stacks in `cdk-environment/`, both built from this shared `infra/` tree)

## 1. Where the alarms come from

### Per-Lambda alarms (the bulk: 123 of ~163)

`infra/main/java/co/uk/diyaccounting/submit/constructs/Lambda.java:124-203` creates 4 alarms for
every Lambda/ApiLambda instance: `{fn}-errors`, `{fn}-throttles`, `{fn}-high-duration-p95`, and
`{fn}-log-errors` (the last backed by a `MetricFilter` scanning logs for `ERROR|Exception|...`,
which is also a billed custom metric, not just an alarm).
`infra/main/java/co/uk/diyaccounting/submit/constructs/AsyncApiLambda.java:49-137` adds 3 more per
async pair (ingest + worker): `{dlq}-not-empty`, `{worker}-errors`, `{queue}-message-age`, for 7
total per async Lambda.

27 Lambda-construct instances exist across the codebase: 19 sync (16 `ApiLambda`, 2 plain `Lambda`
not HTTP-routed — `reconcileLambda` in AccountStack and `telegramForwarderLambda` in OpsStack — plus
`SelfDestructStack`'s lambda, CI-only) and 5 async pairs (2 in AccountStack, 3 in HmrcStack).
19×4 + 5×7 = 111. Three more sync instances live in environment-level stacks — `webhookLambda`
(BillingWebhookStack), `transformLambda` (AnalyticsStack), and `TableChangeDelivery`'s consumer
Lambda (`AnalyticsStack.java:366`) — adding 12 more. 111 + 12 = 123, matching the backlog figure
exactly.

### ApiStack: the 5xx alarm plus a duplicate per route (22)

`ApiStack.java:224-236` creates one `{prefix}-api-5xx` alarm for the whole HTTP API (fine, this is
the right level).

`ApiStack.java:436-445`, inside `createRouteForLambda` (called once per HTTP route at
`ApiStack.java:285-286`), creates a second alarm — `{fn}-lambda-errors-{method}-{path}` — on the
exact same `fn.metricErrors()` metric that `Lambda.java:124-136` already alarms on as `{fn}-errors`,
same threshold (≥1/5min), same comparison operator. This is a straight duplicate: 21 of the 27
Lambda instances are HTTP-routed and get both alarms. **Bug/oddity**: `ApiStack.java:436` and
`Lambda.java:124` alarm on the same metric under two different names with no functional difference
between them.

### OpsStack: canaries, GitHub probe, and an unfiltered Telegram fan-out (3 alarms + 1 rule of note)

`OpsStack.java:412` (`HealthAlarm`) and `OpsStack.java:450` (`ApiAlarm`) watch the two Synthetics
canaries (health check, API check), each on a 51-minute schedule (`OpsStack.java:120-122`, default
`canaryIntervalMinutes() = 51`, matching `AWS_COSTS.md`'s stated post-optimization cadence).
`OpsStack.java:300` (`GithubProbeAlarm`) watches a custom metric fed by the probe-test
GitHub Actions workflow, 2-hour window.

**Bug/oddity, more significant**: `OpsStack.java:272-281` creates `AlarmStateChangeRule`, an
EventBridge rule on the default bus matching `source: aws.cloudwatch`,
`detail-type: "CloudWatch Alarm State Change"` — with no `resources` filter, so it matches every
alarm in the account, not just this deployment's own alarms. Because OpsStack (and this rule) is
created once per **app deployment**, every concurrent deployment in an account runs its own copy of
this unfiltered rule. With N concurrent deployments (CI regularly runs several — `AWS_COSTS.md`
records 39 distinct deploy windows across 23 branches in one month), a single alarm state change
anywhere in the account fires the Telegram forwarder Lambda N times, once per deployment's copy of
the rule. This doesn't cost CloudWatch money (EventBridge rules on AWS-service events are free
here per the comment at `OpsStack.java:246`), but it does mean Telegram alerting is currently
noisier under concurrent CI activity than the single-alarm intent suggests.

### EdgeStack: WAF and certificate alarms (4, in us-east-1)

`EdgeStack.java:268-341`: `{prefix}-waf-rate-limit` (≥50 blocks/5min), `{prefix}-waf-attack-signatures`
(≥5/5min, Common Rule Set), `{prefix}-waf-known-bad-inputs` (≥5/5min), and `{prefix}-cert-expiring`
(ACM `DaysToExpiry` < 30). These run in us-east-1 (CloudFront's region) and forward state changes to
eu-west-2 for the Telegram rule — reasonable, low-cardinality, high-value alarms.

### Environment-level extras (15, shared across all deployments in an environment)

- `ObservabilityStack.java:326,336`: RUM LCP p75 and RUM JS-error alarms (2).
- `ObservabilityStack.java:663,681`: `BundleCapReachedAlarm`, `HmrcSubmissionFailureAlarm` (2) —
  business-signal alarms, not infra.
- `AnalyticsStack.java:688,704`: Firehose delivery-failed and put-failed (2).
- `analytics/AnalyticsDashboard.java:239,250`: metrics-publish errors and DLQ depth (2).
- `analytics/DataQuality.java:324,335,350`: data-quality-run errors, DLQ depth, and rules-failed (3).
- `IngestionStack.java:361-407` (`registerScheduledJob`, called twice — `IngestionStack.java:242`
  Stripe reconciliation and `IngestionStack.java:332` GA4 report pull): 2 alarms each, 4 total.
  These use a 24-hour evaluation window on daily/weekly batch jobs — appropriately quiet, low risk
  to cut.

### No composite alarms anywhere

Zero `CompositeAlarm` usage across the whole `infra/` tree (`grep -rn "CompositeAlarm"` returns
nothing). Every one of the ~163 alarms evaluates independently. Combined with the unfiltered
`AlarmStateChangeRule`, this means the alarm layer does no consolidation at all — CloudWatch alarms
are billed per-alarm-per-metric with no folding, and the notification layer does no deduplication
either.

## 2. Signal value — no live history available

`describe-alarm-history` calls were not runnable (expired SSO on both `submit-prod` and
`submit-ci`). No never-fired / fired-recently breakdown is possible from this audit. What CDK
sources do establish, indirectly:

- `RUNBOOK_INFORMATION_SECURITY.md` and `_developers/backlog/ALARM_VALIDATION_STRATEGY.md` both
  describe most Lambda/API/RUM/DLQ alarms as "silent" — no `.addAlarmAction()` / SNS target in the
  CDK for the bulk of them (confirmed: `Lambda.java`, `AsyncApiLambda.java`, and `ApiStack.java`'s
  duplicate alarm never call `.addAlarmAction`). They rely entirely on the unfiltered
  `AlarmStateChangeRule` in OpsStack to reach Telegram.
- Only `alertTopic` (canary/health alarms) and `securityFindingsTopic` (the GuardDuty/SecurityHub/
  IAM/security-group/access-key/root EventBridge rules in `ObservabilityStack.java:347-484`) are
  explicitly wired to SNS in the CDK.
- The 24-hour-window scheduled-job alarms (Stripe reconcile, GA4 pull, data-quality run, analytics
  metrics publish) are structurally unlikely to have ever fired outside a real incident — they
  alarm on `errors >= 1` for jobs that run once a day/week and would need an actual failure to
  breach.

**Recommended follow-up once SSO is live**: run `describe-alarm-history` with
`--history-item-type StateUpdate` over the last 90 days for every alarm matching the CI and prod
resource-name prefixes; anything with zero `StateUpdate` events besides the initial `INSUFFICIENT_DATA`
→ `OK` transition at stack creation has never told anyone anything and is the first cut candidate.

## 3. Cost estimate

Using published CloudWatch pricing (standard-resolution alarms $0.10/alarm/month, first 10 free
per account; custom metrics $0.30/metric/month, first 10 free; canary runs $0.0012/run):

| Item | Count | Rate | Monthly |
|---|---:|---:|---:|
| Alarms, one environment + one deployment | ~163 (153 billable after 10 free) | $0.10 | ~$15.30 |
| Custom metrics (27 `{fn}-log-errors` MetricFilters, 17 billable after 10 free) | 17 | $0.30 | ~$5.10 |
| Synthetics canaries, 2 × every 51min | ~1,694 runs/mo | $0.0012 | ~$2.00 |
| Dashboards (ops + analytics, if both exist) | 2 | $3.00 | ~$6.00 |
| RUM | — | — | ~$1.00 |
| **Subtotal, one environment (prod-typical)** | | | **~$29.40** |

`AWS_COSTS.md:128` currently estimates prod's whole CloudWatch line at **$7/month** on the
assumption of "~20 alarms". The real CDK-sourced count is ~163 alarms for prod alone (one
deployment), which puts the alarm line by itself above that $7 figure before dashboards, RUM, or
custom metrics are added. This estimate should be treated as the more accurate one going forward;
`AWS_COSTS.md`'s per-account CloudWatch actuals table (post-separation, Feb 2026: submit-prod
$1.42/2 days, submit-ci $0.40/2 days) is measured and not in question — only the itemised "~20
alarms" assumption feeding the target-state estimate at line 128 is stale.

For CI, the app-level 136 alarms exist once per **concurrent** deployment, not once per environment.
`AWS_COSTS.md`'s own stack-hours model (131.4 stack-hours across 39 deploy windows in 30 days, ≈0.18
average concurrent deployments) gives an average CI app-alarm cost of roughly 136 × $0.10 ×
(131.4/720) ≈ **$2.48/month**, on top of the ~27 shared env-level alarms once per environment. This
is consistent with `AWS_COSTS.md`'s own CI app CloudWatch line ("~$1.00"), and confirms the
per-deployment alarm count — not the environment-level one — is what scales with CI branch churn.
The historical actual `CW:AlarmMonitorUsage $19.62 / 206 alarm-months` (pre-optimization, 31 days,
`AWS_COSTS.md:445`) is the same mechanism at a busier point in the CI cycle.

## 4. Recommendations

### Cut 1: drop ApiStack's duplicate per-route Lambda-errors alarm

**File**: `infra/main/java/co/uk/diyaccounting/submit/stacks/ApiStack.java:436-445`
**What**: delete the `{fn}-LambdaErrors-{keySuffix}` alarm inside `createRouteForLambda`. It
duplicates `Lambda.java:124-136`'s `{fn}-errors` alarm on the identical metric, threshold, and
comparison operator.
**Savings**: ~21 alarms removed per app deployment, ×$0.10/month ×(however many deployments are
live) — roughly $2.10/month per environment with one deployment, more under CI churn.
**Risk**: none. The alarm being removed is a byte-for-byte duplicate of one that stays; no signal
is lost, only a differently-named copy of the same signal.

### Cut 2: fold the unfiltered AlarmStateChangeRule into one place

**File**: `infra/main/java/co/uk/diyaccounting/submit/stacks/OpsStack.java:272-281`
**What**: this rule is unfiltered (matches every alarm account-wide) but is created once per app
deployment. Either move it to an environment-level stack (created once per environment, not once
per deployment) or add a `resources` filter scoping it to alarms this specific deployment owns.
**Savings**: not a CloudWatch dollar saving (EventBridge rules on AWS-service events are free per
the comment at `OpsStack.java:246`), but removes N-times-duplicated Telegram notifications under
concurrent CI deployments — a genuine signal-quality fix, not just cost.
**Risk**: low. Moving it to an environment stack changes nothing about detection; it removes
redundant delivery. A `resources` filter is more surgical but needs each deployment's alarm ARNs
enumerated, which the CDK doesn't currently expose in one place.

### Cut 3: consolidate the 4 per-Lambda alarms into fewer, composite signals

**File**: `infra/main/java/co/uk/diyaccounting/submit/constructs/Lambda.java:122-203`
**What**: `Errors`, `Throttles`, `HighDurationP95`, `LogErrors` fire independently per function.
A `CompositeAlarm` (`software.amazon.awscdk.services.cloudwatch.CompositeAlarm`, unused anywhere in
this codebase today) grouping the 4 per-function alarms with `AlarmRule.anyOf(...)` would still
detect every condition but bill as 1 composite alarm ($0.50/month) instead of 4 standard alarms
($0.40/month combined) — at today's alarm count this is roughly cost-neutral per function, but it
collapses 108 (27×4) individually-evaluated CloudWatch checks into 27, which is where the real
saving is: fewer separate Alarm resources to evaluate, list, and reason about, and one Telegram
notification per function-health-event instead of up to 4.
**Savings**: modest direct dollars (~break-even at current per-alarm/composite pricing), but cuts
the per-deployment alarm count from ~136 toward ~55 (27 composites + the non-Lambda alarms), which
is the number that matters for "the largest recurring CloudWatch cost line" the backlog item names.
**Risk**: medium. A composite alarm's `AlarmRule` still needs the 4 child alarms to exist (they're
the terms in the boolean rule) — CDK composite alarms wrap existing alarms, they don't replace them
for billing purposes unless the underlying alarms are also suppressed from individual notification.
The saving is in **notification consolidation**, not raw alarm-resource count, unless paired with
Cut 2 (routing only the composite's state changes to Telegram, not each child's). Needs a design
pass before implementing, not a blind cut.

### Lower-priority: the 24h-window scheduled-job alarms are cheap and quiet already

`IngestionStack.java:384-404`, `analytics/AnalyticsDashboard.java:239-260`,
`analytics/DataQuality.java:324-346` — 8 alarms total across 4 daily/weekly batch jobs, each on a
24-hour evaluation window. These are exactly what "actionable, rarely-firing" alarms should look
like. Not a cut candidate; flagged here only so a future pass doesn't lump them in with the
per-Lambda sprawl by pattern-matching on "8 more alarms found."

## 5. Where scan-detection and data-theft-detection (issues #9/#10) slot in

`plans/issues/PLAN_ISSUE_9_scan_detection.md` and `plans/issues/PLAN_ISSUE_10_data_theft_detection.md`
both point at a new `infra/main/java/.../stacks/SecurityDetectionStack.java`, shared between the two
issues, wired to the existing `securityFindingsTopic` SNS topic that `ObservabilityStack.java:347-484`
already creates and uses for GuardDuty/SecurityHub/IAM/security-group/access-key/root-activity
EventBridge rules. That topic and its Telegram-adjacent routing pattern is the right integration
point — it already exists, is environment-level (not per-deployment, avoiding the OpsStack
duplication problem above), and the new stack's design should follow the same "EventBridge rule →
SNS → forwarder" shape rather than adding more per-function CloudWatch alarms. Confirmed no
scan-detection or data-theft-detection alarm exists in CDK today
(`grep -rn "scan-detect\|dynamodb-scan\|DataTheft" infra/main/java/` returns nothing) — this is a
genuine gap, not yet-undiscovered coverage.

Two things this audit surfaces that the #9/#10 work should account for before adding more alarms:

1. Land Cut 2 (the unfiltered `AlarmStateChangeRule`) first, or the new detection alarms inherit the
   same N-times-duplicated Telegram delivery under concurrent CI deployments.
2. `PLAN_ISSUE_10_data_theft_detection.md`'s acceptance criterion 2 — "any IAM principal performing
   `dynamodb:Scan` on customer tables... raises a detection event within 5 min" — should land as
   metric-filter-backed alarms in the new environment-level `SecurityDetectionStack`, not as another
   per-function alarm on the existing Lambda construct; the existing Lambda IAM grants
   (`grantReadData()` includes `Scan` per `ALARM_VALIDATION_STRATEGY.md`'s Level 6 analysis) never
   call `Scan` from app code today, so any `Scan` CloudTrail event on a customer table is a clean,
   near-zero-false-positive signal — exactly the kind of alarm this audit found the codebase
   currently lacks.
