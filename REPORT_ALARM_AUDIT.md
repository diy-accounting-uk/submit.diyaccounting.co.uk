# REPORT_ALARM_AUDIT

Every app deployment (AuthStack, HmrcStack, AccountStack, BillingStack, ApiStack, OpsStack,
EdgeStack) creates about 95 CloudWatch alarms: 89 standard and 6 composite. The shared
environment stacks (ObservabilityStack, AnalyticsStack, IngestionStack, and friends) add another
24, once per environment: 22 standard and 2 composite. One environment with a single active
deployment — prod, most of the time — carries roughly 119 alarms: 111 standard and 8 composite.
CI, which runs several concurrent feature-branch deployments, multiplies the 95 by however many
are live at once.

- Audited: 2026-09-04, recounted from the code that landed `PLAN_ALARM_CONSOLIDATION.md`'s design
- Method: CDK source read only — see "What was skipped" below
- Source: `infra/main/java/co/uk/diyaccounting/submit/` (application stacks in `cdk-application/`,
  environment stacks in `cdk-environment/`, both built from this shared `infra/` tree)

## What was skipped

No live `describe-alarms` inventory and no alarm-history / fired-vs-never-fired data — this
report is CDK-source-only, same as the original 2026-08-31 pass:

- Cost estimates use published CloudWatch standard pricing ($0.10/alarm/month, first 10 free per

## 1. Where the alarms come from

### Per-Lambda alarms (the bulk: 88 of 111 standard)

`infra/main/java/co/uk/diyaccounting/submit/constructs/Lambda.java:145-197` creates 2 alarms for
every Lambda/ApiLambda instance: `{fn}-errors` and `{fn}-log-errors` (the latter backed by a
`MetricFilter` scanning logs for `ERROR|Exception|...`, which is also a billed custom metric, not
just an alarm). `Throttles` and `HighDurationP95` were cut: a throttle at this traffic level is not
reachable and surfaces as an API 5xx anyway, and p95 near timeout is a leading indicator for a
timeout that arrives as an error.

`infra/main/java/co/uk/diyaccounting/submit/constructs/AsyncApiLambda.java:57-146` adds
`{dlq}-not-empty`, `{worker}-errors` and `{queue}-message-age`, for 5 total per async pair (the 2
base checks plus these 3). All 5 stay as individually-evaluated standard alarms — a composite
alarm wraps existing alarms, it does not replace them for billing — but none of the 5 routes to
Telegram or GitHub on its own any more; they are terms in the owning stack's composite instead
(see "Composite alarms" below).

32 Lambda-construct instances exist across the codebase for one prod deployment plus the shared
environment stacks: 24 sync (17 `ApiLambda`, 7 plain `Lambda` not HTTP-routed — `reconcileLambda`
in AccountStack, `telegramForwarderLambda` and `alarmToGithubIssueLambdaConstruct` in OpsStack,
`wafScanDetectLambda` in EdgeStack, `transformLambda` in AnalyticsStack, `webhookLambda` in
BillingWebhookStack, and `TableChangeDelivery`'s consumer Lambda — plus `SelfDestructStack`'s
lambda, CI-only) and 8 async pairs (2 in AccountStack — `requestBundlesAsyncLambda`,
`bundleDeleteAsyncLambda` — and 6 in HmrcStack — `submitVatLambdaUrlOrigin` and the
obligation/liabilities/payments/penalties/return-get read endpoints, all `AsyncApiLambda` since
the VAT read-endpoints work grew past the original audit's count of 5). 24×2 + 8×5 = 88.

21 of the 24 sync instances and all 8 async pairs live in app-level stacks (82 standard alarms);
3 sync instances live in environment-level stacks — `webhookLambda`, `transformLambda`, and
`TableChangeDelivery`'s consumer Lambda — for 6 more. 82 + 6 = 88.

### ApiStack: just the 5xx alarm now

`ApiStack.java:224-236` creates one `{prefix}-api-5xx` alarm for the whole HTTP API. The per-route
duplicate that `createRouteForLambda` used to add on the same `fn.metricErrors()` metric that
`Lambda.java` already alarms on as `{fn}-errors` is gone — `ApiStack.java` no longer creates a
`{fn}-lambda-errors-{method}-{path}` alarm at all. 1 alarm now, not the 22 the previous audit
found.

### OpsStack: canaries and a filtered Telegram fan-out

`OpsStack.java:412` (`HealthAlarm`) and `OpsStack.java:450` (`ApiAlarm`) watch the two Synthetics
canaries (health check, API check), each on a 51-minute schedule. The GitHub probe alarm no longer
lives here: it moved to the environment-level `ObservabilityStack` (see "Environment-level
extras" below), so one alarm object survives every deployment instead of each new deployment
spawning its own against the same environment-wide `behaviour-test` metric.

The `AlarmStateChangeRule` EventBridge rule that used to match every alarm in the account,
regardless of which deployment or environment owned it, now filters on `detail.alarmName` by a
`prefix` match against this deployment's own resource-name prefix or the environment's shared
prefix. Concurrent CI deployments no longer each fire Telegram/GitHub for every alarm state change
account-wide.

### EdgeStack: WAF and certificate alarms (4, in us-east-1)

`EdgeStack.java:268-341`: `{prefix}-waf-rate-limit` (≥50 blocks/5min), `{prefix}-waf-attack-signatures`
(≥5/5min, Common Rule Set), `{prefix}-waf-known-bad-inputs` (≥5/5min), and `{prefix}-cert-expiring`
(ACM `DaysToExpiry` < 30). These run in us-east-1 (CloudFront's region) and forward state changes to
eu-west-2 for the Telegram rule — reasonable, low-cardinality, high-value alarms. Unchanged from
the original audit.

### Composite alarms: one per stack, not zero

`Lambda.stackHealthAlarm` fans every health check of every Lambda construct a stack owns into one
`CompositeAlarm`, named `{resourceNamePrefix}-{stackShortName}-stack-health`. 9 stacks call it:
`auth`, `hmrc`, `account`, `billing`, `ops`, `edge` (app-level, one per deployment), `analytics`,
`billing-webhook` (environment-level, one per environment), and `self-destruct` (app-level, ci
deployments only).

One prod deployment plus its environment carries 8 composites (6 app + 2 env). A ci deployment
adds a 9th (`self-destruct-stack-health`). The children stay as individually-billed standard
alarms — they are the terms of the composite's `AlarmRule.anyOf(...)` — so compositing adds a
billing line rather than removing one; the saving is in notification consolidation (one Telegram
message per stack-health event instead of up to 5 per async pair) and in how many separate alarm
resources a person has to read, not in raw alarm count.

### Environment-level extras (16, shared across all deployments in an environment)

- `ObservabilityStack.java`: RUM LCP p75 and RUM JS-error alarms (2); `BundleCapReachedAlarm`,
  `HmrcSubmissionFailureAlarm` (2) — business-signal alarms, not infra; the GitHub probe alarm
  (1), moved in from OpsStack and widened from a 2-hour to a 5-hour period so every rolling window
  is guaranteed a datapoint against `probe-test.yml`'s 4-hour cron.
- `AnalyticsStack.java`: Firehose delivery-failed and put-failed (2).
- `analytics/AnalyticsDashboard.java`: metrics-publish errors and DLQ depth (2).
- `analytics/DataQuality.java`: data-quality-run errors, DLQ depth, and rules-failed (3).
- `IngestionStack.java` (`registerScheduledJob`, called twice — Stripe reconciliation and GA4
  report pull): 2 alarms each, 4 total. These use a 24-hour evaluation window on daily/weekly
  batch jobs — appropriately quiet, low risk to cut.

2 (RUM) + 2 (bundle/HMRC) + 1 (probe) + 2 (Firehose) + 2 (AnalyticsDashboard) + 3 (DataQuality) +
4 (IngestionStack) = 16.

This list does not include `SecurityDetectionStack.java` (DynamoDB scan/GetItem-volume/salt-read
alarms, 3) or `ScanDetectionStack.java` (404 scan-rate errors/missed, 2), both environment-level
and both added since the original audit for issues #9/#10. They sit outside the scope of this
recount, which tracks only the alarm cuts from `PLAN_ALARM_CONSOLIDATION.md`.

## 2. Signal value — no live history available

Same caveat as the original audit: no `describe-alarm-history` data, so no never-fired /
fired-recently breakdown is possible from this recount. What CDK sources establish, indirectly:

- `Lambda.java`, `AsyncApiLambda.java`, and `ApiStack.java`'s 5xx alarm never call
  `.addAlarmAction()` — they rely on the `AlarmStateChangeRule` in OpsStack, now filtered by
  prefix, to reach Telegram.
- Only `alertTopic` (canary/health alarms) and `securityFindingsTopic` (the GuardDuty/SecurityHub/
  IAM/security-group/access-key/root EventBridge rules in `ObservabilityStack.java`) are explicitly
  wired to SNS in the CDK.
- The 24-hour-window scheduled-job alarms (Stripe reconcile, GA4 pull, data-quality run, analytics
  metrics publish) are structurally unlikely to have ever fired outside a real incident — they
  alarm on `errors >= 1` for jobs that run once a day/week and would need an actual failure to
  breach.

## 3. Cost estimate

Using published CloudWatch pricing (standard-resolution alarms $0.10/alarm/month, first 10 free
per account; composite alarms $0.50/month; custom metrics $0.30/metric/month, first 10 free;
canary runs $0.0012/run):

| Item | Count | Rate | Monthly |
|---|---:|---:|---:|
| Standard alarms, one environment + one deployment (101 billable after 10 free) | 111 | $0.10 | $10.10 |
| Composite alarms | 8 | $0.50 | $4.00 |
| Custom metrics (32 `{fn}-log-errors` MetricFilters, 22 billable after 10 free) | 22 | $0.30 | $6.60 |
| Synthetics canaries, 2 × every 51min | ~1,694 runs/mo | $0.0012 | ~$2.00 |
| Dashboards (ops + analytics, if both exist) | 2 | $3.00 | ~$6.00 |
| RUM | — | — | ~$1.00 |
| **Subtotal, one environment (prod-typical)** | | | **~$29.70** |

For a billing-measured view of this same environment, including alarms this CDK-source recount
doesn't cover (`SecurityDetectionStack`, `ScanDetectionStack`), see `PLAN_COST_OPTIMISATION.md`.

For CI, the app-level 95 alarms (89 standard + 6 composite) exist once per **concurrent**
deployment, not once per environment; the 24 shared env-level alarms (22 standard + 2 composite)
exist once per environment regardless of how many deployments are live. The GitHub probe alarm
moving from OpsStack (app-level) to ObservabilityStack (env-level) means it no longer multiplies
with concurrent CI deployments — previously N concurrent deployments each carried their own copy
of the same environment-wide check, each opening its own GitHub issue.

## 4. Lower-priority: the 24h-window scheduled-job alarms are cheap and quiet already

`IngestionStack.java`, `analytics/AnalyticsDashboard.java`, `analytics/DataQuality.java` — 8
alarms total across 4 daily/weekly batch jobs, each on a 24-hour evaluation window. These are
exactly what "actionable, rarely-firing" alarms should look like. Not a cut candidate; flagged
here only so a future pass doesn't lump them in with the per-Lambda sprawl by pattern-matching on
"8 more alarms found."

## 5. Where scan-detection and data-theft-detection (issues #9/#10) landed

`SecurityDetectionStack.java` and `ScanDetectionStack.java` now exist, both environment-level.
`SecurityDetectionStack` wires 3 alarms (DynamoDB customer-table scan, GetItem-volume, salt-secret
unexpected-read) to the `securityFindingsTopic` SNS topic that `ObservabilityStack.java` already
uses for GuardDuty/SecurityHub/IAM/security-group/access-key/root-activity EventBridge rules.
`ScanDetectionStack` adds 2 more (404 scan-rate errors, missed-run). Both follow the
"EventBridge rule/alarm → SNS → forwarder" shape rather than adding more per-function CloudWatch
alarms, and both are environment-level, so they don't multiply with concurrent CI deployments the
way the app-level GitHub probe alarm used to.

These 5 alarms sit outside the headline counts above, which track only the alarm cuts from
`PLAN_ALARM_CONSOLIDATION.md`.
