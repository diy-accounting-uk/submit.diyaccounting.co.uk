# REPORT: Commit authorship and GitHub activity identity, six repositories

Read-only audit, 2026-09-09. Covers `diy-accounting-archive`, `homebrew-diya-gl`,
`root.diyaccounting.co.uk`, `spreadsheets.diyaccounting.co.uk`, `submit.diyaccounting.co.uk` and
`www.diyaccounting.co.uk`. No repository was changed.

## The headline

One GitHub account, `antonycc`, is the recorded author of almost everything these six
repositories contain and almost everything that happens on them. It authored 74 of the 75 issues
in submit, including all 55 raised by a machine. It authored 386 of the 426 issue comments a
machine wrote. It authored 3,094 of submit's 4,107 commits. None of those commits is signed.

So no policy can currently ask "did a person do this?" and get an answer. Every proposed
governance rule in `PLAN_REPOSITORY_AUTOMATION.md` needs that answer.

A second problem sits beside it. Nothing on any public surface tells a reader whether words came
from a person, a template or a model. Not the site, not the support replies, not the alarm
comments, not the commit messages in any form a reader would notice. The site has no AI
disclosure of any kind.

## Two purposes, pulling in opposite directions

Provenance does two different jobs here, and a mechanism that suits one can be wrong for the
other.

**Enforcement.** A policy trusts a claim before it acts. Auto-merge trusts "every commit on this
PR is the owner's". The alarm path trusts "this issue came from a prod alarm". The threat is
forgery: someone or something asserting what is not true. The question is what cannot be edited
away.

**Disclosure.** DIY Accounting tells its readers whether words were written by a person, filled
from a template, or generated by a model. The threat here is omission, not forgery. Nobody gains
by stripping a disclosure label. The risk is that we never apply one, apply it unevenly, or put
it where a reader has to know to look. So the mechanism must make labelling automatic, hard to
skip, and visible to someone who is not looking for it.

The two rank mechanisms differently. Section 6 does the ranking against both.

## 3. The identity classes

The operator named three. Three is not enough, because two of them each split on something a
downstream rule already treats differently.

| Class | Who acts | Downstream difference that justifies the split |
|---|---|---|
| **H. Human operator** | The operator, directly | Only a human closes a human-raised ticket (P1). Only a human's own commits qualify for the narrow auto-merge (P2) |
| **A. Attended agent** | Claude Code in a live session, under an operator direction | A person saw the diff before it was pushed. That is what P2 is really trusting. Splitting it from U is what lets P2 stay true |
| **U. Unattended agent** | A model started by a schedule or an event, with nobody watching | Needs a run budget, a diff-size ceiling and a remedy allow-list (P10, phase 3). An attended session does not |
| **M. Deterministic machine** | A workflow, generator or Lambda with no model | Its output is checkable by re-running it. Needs no model disclosure, only a "templated" one |
| **X. External contributor** | Anyone outside the org | Never authorises a merge (P4). Its issues are triaged, never machine-closed |

Class M splits again, and this one matters more than it looks:

- **M-repo.** Acts on a GitHub event. Its claim is checkable only against GitHub's own record.
- **M-aws.** Acts on an AWS event, and the AWS event still exists. Its claim is checkable by
  re-reading `cloudwatch describe-alarm-history`. That is P3's rung 3 and the strongest proof
  available anywhere in this design.

Keep it as a sub-split rather than a sixth class. It changes what proves a claim, not who acts.

Where each class sits today:

| Class | Today's identity | Distinguishable |
|---|---|---|
| H | `antonycc` | no |
| A | `antonycc` | no |
| U | `antonycc` (Copilot assignment), `github-actions[bot]` and `claude` (alarm triage) | partly |
| M-repo | `antonycc` (support tickets), `github-actions[bot]` (generators), `actions-user` (publish) | partly |
| M-aws | `antonycc` (alarm issues and comments) | no |
| X | the contributor's own account | yes |

## 4. What each class should present

### 4.1 The accounts

| Class | Account | Why |
|---|---|---|
| H, A | `antonycc` | Already the org member and the account GitHub attributes the gmail to. Changing it moves four years of contribution history to a different account for no gain |
| U | GitHub App **`diya-agent`**, acting as `diya-agent[bot]` | An installation token is scoped and short-lived. A PAT sitting in two secret stores is not |
| M-repo, M-aws | GitHub App **`diya-ops`**, acting as `diya-ops[bot]` | Same reason. It also replaces three copies of one PAT with one installation |
| Workflows using `github.token` | `github-actions[bot]` | Already correct. Leave it |
| X | their own account | Already correct |

Two apps, not one. `diya-agent` writes what a model produced. `diya-ops` writes what a
deterministic pipeline produced. A reader needs to tell those apart, and one app cannot present
two names.

A GitHub App costs nothing. A machine **user** account would cost an Enterprise seat, and its PAT
would sit copyable in two places. Prefer the app.

### 4.2 The commit identity

For classes H and A, one author identity everywhere:

```
git config --global user.name  "Antony Cartwright"
git config --global user.email "10074096+antonycc@users.noreply.github.com"
```

The noreply address already appears in 438 co-author trailers in submit, so it is confirmed as
`antonycc`'s. Using it keeps a personal gmail out of six public repositories and attributes
exactly as the gmail does today.

Do not switch to `antony@polycode.co.uk`. That address belongs to `Antony-at-Polycode`, which is
not an org member. Switching would attribute every future commit to a non-member account.

For class U, the workflow commit identity becomes the app's:

```
git -c user.name='diya-agent[bot]' \
    -c user.email='<app-id>+diya-agent[bot]@users.noreply.github.com' commit ...
```

That replaces `alarm-triage.yml`'s current `user.name='claude-alarm-triage'` and
`user.email='noreply@anthropic.com'`, which attributes our commits to the GitHub user `claude`.

Class M keeps `github-actions[bot]@users.noreply.github.com`. `publish.yml`'s `action@github.com`
goes, because it attributes to `actions-user`.

### 4.3 The trailer

One form, Anthropic's own, on every commit a model helped write:

```
Co-Authored-By: Claude <noreply@anthropic.com>
```

No model name, no context-window note, no version. The version belongs in the session log, and
the long form is signal 8 in `PLAN_FLAGGED.md`.

Keep `Claude-Session:` as a second trailer. It is ours, it is honest, and it is the only link back
to what actually happened. Mark it in the repo's own docs as our convention, not a standard.

Put both in each repository's `CLAUDE.md` as an explicit instruction, so the form stops depending
on what a session prompt happened to say that day.

## 5. What proves a claim, for enforcement

Ranked strongest first. Editable text is at the bottom.

| Rank | Mechanism | What it proves | What defeats it |
|---|---|---|---|
| 1 | Re-read the source of truth (`describe-alarm-history` for the alarm and window the issue names) | The event happened | Nothing, short of AWS itself. It depends on no secret staying secret |
| 2 | A verified commit signature | The holder of a key registered to that account produced this exact tree | Losing the key |
| 3 | A GitHub App installation as the actor (`user.type: Bot`, fixed slug) | That app made the call. The token is short-lived and cannot be lifted from a run | Compromising the app's private key |
| 4 | The API-recorded author (`issue.user`, `comment.user`, PR author) | Which credential made the call. Useless while one credential serves five purposes | Holding the credential |
| 5 | An HMAC over the machine facts | The key holder composed those facts | The key leaking |
| 6 | A machine user account's PAT | The same as 4, but the credential sits copyable in two secret stores | Reading either store |
| 7 | A label such as `origin:agent` | Intent when applied. Any collaborator with write can add or remove it | Anyone with write |
| 8 | A body footer or a commit trailer | Nothing. Free text | Anyone editing it |

The rule this gives: **gate on 1, 2 and 3. Never gate on 7 or 8.**

Recommend rank 1 and rank 3 together for the alarm path, and skip rank 5. An HMAC adds a key to
manage and proves less than re-reading CloudWatch.

## 6. The same mechanisms, ranked for disclosure

Disclosure asks a different question: would a reader who is not looking notice, and does the
mechanism apply itself without anyone remembering?

| Mechanism | Enforcement | Disclosure | Where it is strong for one and weak for the other |
|---|---|---|---|
| Bot account or App as the actor | **strong** | **strong** | The only mechanism strong for both. The name and avatar sit next to every comment, exactly where a reader already looks, and nobody has to remember to add it |
| Re-reading the source of truth | **strongest** | **none** | Perfect proof, invisible to a reader. It happens in a workflow log |
| Commit signature | **strong** | **weak** | A "Verified" badge tells a reader the key holder, not whether a model wrote the code |
| A visible in-body banner ("written by a model, run link") | **none** | **strong** | Editable, so worthless as proof. But a person skimming sees it, and a workflow can append it every time without anyone deciding to |
| A `origin:*` label | **none** | **adequate** | Visible on the issue list, so it works for skimming. Any collaborator can remove it, so it proves nothing |
| A commit trailer | **none** | **near zero** | Almost nobody reads trailers. It is an audit aid, not a disclosure |
| An issue-form field | **none** | **adequate at creation** | Editable afterwards. Fine for routing, useless as proof |
| A PR body sentence | **none** | **adequate** | Readers do read PR bodies. Editable, so no proof |

Two conclusions fall out.

**Disclosure needs automation more than it needs strength.** The threat is forgetting. So the
mechanism must be a step in the path, not a habit. A composite action that appends a footer, or an
app identity that applies itself, both survive a forgetful author. A convention does not.

**One mechanism does both jobs, so build it first.** A distinct bot identity proves which
credential acted and shows a reader who wrote the words, in one move.

### 7.1 Where to draw the line, and why

Over-labelling costs real attention. If every commit, comment and page carries a machine banner,
readers stop seeing them and the label stops meaning anything.

The line: **disclose where a reader could reasonably take the words for a person's own, and where
knowing would change how they read them.**

That gives four rules.

- **Disclose on anything in a human voice.** A support reply, a comment answering a person, a
  post, an article. The reader is forming a view about who is talking to them.
- **Disclose once per artefact, at the top or in the byline.** Not per paragraph, not per section.
- **Do not disclose mechanical output.** A generated spreadsheet, a version bump, a dependency PR,
  a DORA row. Nobody thinks a person hand-typed those, and a banner on each is noise.
- **Do not put a banner on a commit.** The bot identity and the trailer already carry it. A commit
  message with a machine banner on top of an author avatar that already says machine is the
  clearest case of a label that stops being read.

By that line, the alarm repeat comment gets disclosure because it appears under a person's avatar
and could be taken for his words. The nightly package generation does not, because
`github-actions[bot]` committing a file called `bst-2026.xlsx` already says everything.

### 7.2 Follow the existing conventions where they exist

Where a convention exists, use it and say so. Where none does, propose one and mark it as ours.

| Need | Existing convention | Source |
|---|---|---|
| Attributing a model's contribution to a commit | `Co-Authored-By: Claude <noreply@anthropic.com>` | Anthropic's own, what Claude Code writes by default |
| Presenting a non-human actor on GitHub | A GitHub App, rendering as `name[bot]` with `user.type: Bot` | GitHub's own machinery, the same one `dependabot[bot]` and `copilot-swe-agent[bot]` use |
| A machine committing in Actions | `github-actions[bot] <github-actions[bot]@users.noreply.github.com>` | GitHub's documented identity. Already used correctly in five repositories |
| Turning off GitHub's AI contribution classifier | Settings, Code security and analysis, AI-powered features | GitHub, per `PLAN_FLAGGED.md` |
| Linking a commit back to the session that made it | none | **Ours.** `Claude-Session:` trailer. Mark it as a local convention |
| An in-body disclosure banner on a machine-written comment | none published | **Ours.** Propose one wording and use it on every surface |
| Labelling a machine-generated web page | none published | **Ours.** Propose a byline, not a banner |

Two proposed forms, marked as ours.

For a machine-written GitHub comment, one line at the end:

```
_Written by claude-sonnet-4-5 in [alarm-triage #1234](<run url>). Not reviewed by a person._
```

For a generated article or knowledge-base page, a byline under the title, not a banner:

```
Drafted from DIY Accounting support correspondence by a language model.
Reviewed by Antony Cartwright, <date>.
```

If nobody reviewed it, say that instead. A byline a reader can check beats a banner they learn to
skip.

## 9. The migration, in order, and what breaks

**Step 1. Signing.** Register `id_antony_polycode_mbp_2025.pub` on `antonycc` as a *signing* key,
which is a separate registration from the authentication key already there. Then:

```
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_antony_polycode_mbp_2025.pub
git config --global commit.gpgsign true
```

Nothing breaks. Old commits stay unsigned. New commits show "Verified". Do not require signatures
in any ruleset until a few weeks of commits have landed signed, because a rule added on day one
blocks every worktree and CI path that has not picked up the config.

**Step 2. The author email.** Set `user.email` to
`10074096+antonycc@users.noreply.github.com`. This attributes exactly as the gmail does, because
both resolve to `antonycc`. Contribution graphs are unaffected. Do not rewrite history: 3,791
commits would change SHA, every open branch would need rebasing, and mass history rewriting on a
public repository is itself one of the shapes `PLAN_FLAGGED.md` warns about.

**Step 3. The apps.** Create `diya-ops` and `diya-agent`, install both on the org, store each
private key in Secrets Manager. Change the three Lambdas to mint an installation token instead of
reading a PAT. Change `alarm-triage.yml`'s commit identity and its `gh` token.

What breaks: the 55 existing `[ALARM]` issues stay authored by `antonycc` forever, so any origin
check must handle a cutover date. Say so in the check rather than backfilling.

**Step 4. Retire the PATs.** Delete `ISSUE_BOT_TOKEN` and `PERSONAL_ACCESS_TOKEN` after the apps
are proven. `securityLakeNightly.js` reads code-scanning, Dependabot and secret-scanning alerts, so
the `diya-ops` app needs those read permissions before the PAT goes.

**Step 5. Disclosure.** The footer composite action, the labels, the PR template, the byline
decision. These are independent of everything above and can land in any order.

**Step 6. The rules.** Once signed commits are the norm, add a signature-required rule to all six
rulesets, enable `root`'s, and create one for `homebrew-diya-gl`.

### What this does not touch

Contribution attribution for the 693 commits authored `antony@polycode.co.uk` and the 50 authored
from two employer addresses. Those stay where they are. Rewriting them costs more than it buys.
